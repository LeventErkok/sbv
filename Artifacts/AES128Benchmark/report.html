SBV's block-encryption function is 4.0× the size of BearSSL's, and its key schedule is far larger still (generated straight-line code, not timed here). The generated encryptor has no round loop and carries four separate 1 KiB lookup tables plus a 256-byte S-box. Each ordinary round computes four words, each using four table lookups combined with XORs; the final round uses the S-box. BearSSL's aes_big keeps one table, derives the other three by rotating its entries, and loops over rounds. tiny-AES-c computes each byte with an S-box and xtime arithmetic. That is consistent with SBV trading space (code and cache footprint) for fewer instructions per block, but this benchmark did not vary table size or unrolling independently, so it shows a correlation in these three implementations, not an isolated cause. tiny-AES-c's object also contains decryption and key expansion, which were not separated in this measurement, so its total overstates an encrypt-only build.

What was measured

Each iteration encrypts an immutable buffer of independent 16-byte blocks into a separate output buffer. The same expanded key is reused. Key expansion, allocation, input generation, and validation occur before timing. No output block feeds the next input. All implementations receive identical input bytes.

SBV uses its generated block-encryption function with a 44-word expanded encryption key. For SBV the timed adapter loads and stores big-endian words; SBV_native_words calls the same function on pre-converted 32-bit words, which isolates the generated code from that adapter. BearSSL uses its internal single-block br_aes_big_encrypt primitive directly; tiny-AES-c uses AES_ECB_encrypt. Their in-place APIs receive a 16-byte copy from the input. All paths include the work needed for the same byte-buffer interface. There is no padding or chaining between blocks.

OpenSSL uses AES-128-ECB through the default provider and EVP_EncryptUpdate, with padding disabled. The cipher, context, key setup, and a first encryption call are completed before timing. OpenSSL_EVP_block calls EVP once per block; OpenSSL_EVP_bulk calls it once per entire buffer, allowing internal parallel processing and amortizing EVP overhead. Both include EVP return-value and output-length checks. The harness uses OpenSSL's runtime dispatch.

Library: OpenSSL 3.6.3 9 Jun 2026; provider: default; detected capabilities: CPUINFO: OPENSSL_armcap=0x87d. OpenSSL is a prebuilt installed library; it does not share the portable C compiler flags. Its own build flags are recorded in the raw JSON.

The recorded ARM capability mask includes the hardware AES bit (1 << 2), defined in OpenSSL arm_arch.h. This identifies dispatch eligibility, not an instruction trace.

Google Benchmark uses 0.2 seconds of warmup, a minimum 0.5 seconds per measurement, and nine randomly interleaved repetitions per case. Tables show the median thread CPU time normalized per block. Throughput is calculated from that median; CV is the sample standard deviation divided by the mean. Raw JSON also contains wall times. Compiler barriers make output writes observable once per batch. The three portable C implementations use Apple clang version 21.0.0 (clang-2100.3.34.2). Recorded build flags: -O3 -DNDEBUG; no LTO; no explicit architecture flags. Google Benchmark build: release.

Validation and interpretation

Before timing, all four implementations pass the FIPS-197 Appendix C.1 AES128 known-answer vector and agree on 1,024 deterministic pseudorandom key/plaintext pairs. A separate validation run is saved in validation.txt. OpenSSL bulk calls and continued context reuse are also checked at all buffer sizes.

These are warm-buffer, single-thread measurements, including function-call and adapter overhead. Larger buffers amortize benchmark-loop overhead; the portable implementations and OpenSSL block path still make one encryption call per block. OpenSSL bulk makes one call per buffer. The process was not pinned to a CPU, and system load, scheduling, and frequency changes can affect results. Starting load averages reported by Google Benchmark: [3.39648, 3.03711, 2.99365]. Min–max and CV describe nine repetitions, not confidence intervals.

The saved benchmark console output warns that the CPU frequency metadata may be unreliable. The reported ns/block and MiB/s use CPU timers, not that frequency estimate.

The benchmark waits until the 1-minute load average is below 4.5 on a host with 18 logical CPUs before timing; it waited 0 s and started at load 3.40. The threshold is configurable, and passing it does not establish that the machine was idle. Background activity, thermal management, and scheduling can affect results. Small differences between implementations should not be generalized without repeating them elsewhere.

This comparison does not measure cold caches, key expansion, decryption, or authenticated encryption. The three portable implementations use data-dependent table lookups; the comparison makes no constant-time security claim. OpenSSL uses runtime dispatch and may select architecture-specific implementations; interpret its timings alongside the recorded capabilities above.
